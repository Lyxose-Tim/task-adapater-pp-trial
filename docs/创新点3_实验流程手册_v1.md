## 〇、本轮仓库核查的四条新确认信息（先读这个）

1. **官方未提供预训练权重。** README 只有文件结构说明，无权重下载链接；config 里的 `load_weights/checkpoint` 仅用于加载你自己训出的 `.tar`。→ 此前挂账的"官方权重可用性"事项就此关闭：**诊断之前必须自训一版基线**，阶段 0 不可跳过。
2. **此前梳理的三处代码隐患在当前代码中原样存在**，精确位置见 §1.3；其中 P1、P2 对创新点 3 的分支级诊断是**致命的**，必须先修。
3. **新观察 O-1（重要）**：语义顺序适配器（O-MSA）在"3 段子动作"这条轴上**疑似排列等变**——`module_sem_adapter.py` 的 ResidualAttentionBlock 中，x3 分支把 [77, 3, 512] 重排为 [3, 77, 512] 后做**无因果掩码**的自注意力（`use_mask=False`），且该轴上**没有任何位置编码**；adapter/MLP/LN 均逐点作用。若成立，则"打乱 3 段子动作顺序"只会把 3 个输出特征做同样的重排——**模型对文本顺序的全部敏感性都来自式(16) 的"阶段索引 ↔ 帧窗口"耦合**。这既是给论文的锐利机制论据（"O-MSA 架构上并不编码子动作顺序"），也是 3b 的免费午餐（见 §3.2）。**须先用 §2.3 的等变性单元测试实证，再对外使用该结论。**
4. **新观察 O-2**：查询视频之间存在两处批内交互——(a) 视觉分支 Task-MSA 对 `target_images` 前向时，5 个查询在同一时空位置互相注意（`module_adapter.py` 约 L154–157 的 `(b t) l d -> (t l) b d` 重排）；(b) 对齐模块 CrossAttention 的 `q@k^T` 作用在 [N_Q, N_Q] 上（models.py L79–80 + CrossAttention.forward），即相邻帧对齐是**跨查询批**做的，并非论文读起来的"单视频内相邻帧"。支持↔查询确实隔离（support 与 query 分两次过 `self.feature`，与论文声明一致），但**查询↔查询交互存在**——诊断时帧扰动要对全部查询同步施加（§2.3），这一事实也与 LGA 的"泄露"批评及创新点 4 直接相关，先登记。

## 一、阶段 0：环境、数据、隐患修复与基线（里程碑 M0–M2）

### 1.1 环境搭建（M0）

- 租用 4090 单卡（24GB 即可起步）。依赖按 `requirements.txt`：torch 2.2.2+cu121、decord、einops、numpy、Pillow、PyYAML（文件里 PyYAML 写了两行，留一行即可）。
- **坑 A**：requirements 里的 `clip==1.0` 指 OpenAI CLIP（其 GitHub 版安装后版本号即 1.0）；PyPI 上的同名 `clip` 包不是它，直接 `pip install clip` 会装错。用 `pip install git+https://github.com/openai/CLIP.git`。代码只用它的 `clip.tokenize`，但仍必需。
- **坑 B（必改）**：CLIP 权重路径硬编码为作者机器路径，且在**两个文件**里各写了一份——`module_adapter.py:13` 与 `module_sem_adapter.py:9` 的 `CLIP_VIT_B16_PATH = '/home/hanpeiheng/.cache/clip/ViT-B-16.pt'`。改成你自己的 `ViT-B-16.pt`（jit 格式；最省事的获取方式：python 里执行一次 `clip.load("ViT-B/16")`，它会自动下载缓存到 `~/.cache/clip/ViT-B-16.pt`）。两处都要改。
- **坑 C（必改）**：`config.yaml` 默认 `method: ""`，run.py 只认 `'taskadapter'`，不改会直接 `Unknown method`。必改三项：`method: "taskadapter"`、`dataset_base_path: <你的数据根目录>/`、`num_gpus: 1`（默认 3；`distribute_backbone` 用的是 DataParallel，单卡传 `[0]` 没问题）。
- **坑 D**：`dataset.py` L118 的 `num_workers = 48` 按租用机核数调小（8–16 起步）。
- 另注意：run.py 会按数据集**硬编码覆盖**深度参数——somethingcmn 用 `adapter_depth=6, text_depth=2`（config 里的 `text_depth` 字段实际不生效），知道即可，不用动。

### 1.2 数据准备：SSv2-Small（M0）

- 原始数据：SSv2 官方渠道下载（现由 Qualcomm 托管、需注册，视频为 webm）【记忆，以官网为准】。
- 代码读的是**抽好帧的目录**：每个视频一个文件夹，帧名 `img_00001.jpg` 起（`dataset.py` L23/L63 的 `image_tmpl`）。需要自己写抽帧脚本（ffmpeg 即可）。
- 标注文件：每行 `帧目录绝对路径 帧数 类别id`（空格分隔）。仓库根目录的 train/val/test.txt 是作者机器路径的**样例**，格式可参考、内容需自己生成。
- 目录布局被 run.py 硬编码：`{dataset_base_path}/smsm_cmn/annotations/train.txt` 与 `test.txt`（val 与 test 用同一个文件）。
- **类别 id 的对应关系**：id = `utils.py` 中 `smsm_c` 列表（100 类）的下标；语料 `corpus/classes_somethingcmn.yml` 的键就是这些小写类名，值为 `{label, sub_act_en_li:[三句子动作]}`——这正是 3a/3b 的干预对象。
- 划分：SSv2-Small 为 CMN 划分（64/12/24 类，共 100 类）【原文】。生成 annotation 时严格按此划分；README 指向上游仓库 `bedman367/Task-Adapter` 获取训练与数据细节，划分文件以其为准。
- 数据体检清单（跑实验前完成）：每类视频数统计、帧数分布直方图、随机抽 3 个样本可视化确认帧序正确。

### 1.3 三处隐患修复（M1，各自独立 commit）

| 编号 | 位置 | 现象 | 处置 |
|---|---|---|---|
| P1 命名互换 | `models.py:113` 返回 `return sem_dists, dists`；`run.py` L46/L94/L135 接收为 `vis_dis, sem_dis` | 语义分被当成视觉分。融合乘积可交换、终分不受影响，但**任何分支级分析都会张冠李戴** | 统一命名（建议 models.py 改为返回 `(vis_dists, sem_dists)`），run.py 三处接收点同步改 |

附带登记（不改）：CrossAttention 对 somethingcmn **无任何可学参数**（ln_1、to_out 均为 Identity）；两分支相似度均在 fp16 下计算（`utils.py:28`）。

### 1.4 基线复现（M2）

- 流程：改好 config 后 `python run.py`。默认训 10 个 epoch（`warm_up_epoch: 8` 之后才开始验证与存 ckpt），每 epoch 1000 个训练 episode；训练结束自动加载最优 ckpt 跑 10000 episode 测试（每 1000 打印一次滚动均值±CI）。全局种子 916（`setup_seed`）。
- 首跑前先做**小规模全链路试跑**：把 `train_episode`、`test_episode`、`stop_epoch` 临时调小，确认数据管线、显存、日志全通，再放全量；顺手记录单 epoch 耗时与显存峰值（首个需要实测填写的空）。
- 目标参照：论文 SSv2-Small 5-way 1-shot = **63.6**【原文】。建议判据：修复 P1/P2 后的复现值与 63.6 差距明显（如超过 1 个百分点）时，优先排查数据（划分、帧数、采样）而非调参。修复后的复现值记为 **B0**，之后所有实验都对照 B0，不再对照论文数。

## 二、阶段 1：顺序敏感性诊断（3a，M3–M4）

### 2.1 条件矩阵

| 条件 | 文本侧 | 视觉侧 | 说明 |
|---|---|---|---|
| C0 | 正序 | 正常 | 基准（=B0 的评测口径） |
| C1 | 反转 (3,2,1) | 正常 | 最强顺序破坏 |
| C2 | 全部 5 个非恒等排列 | 正常 | 报逐排列与均值 |
| C3 | 正序 | 帧反转 | 视觉侧对照 |
| C4 | 正序 | 帧随机打乱 | 每 episode 固定一个随机排列并记录种子 |
| C5（可选） | 反转 | 帧反转 | 交叉项：文本视觉同时反转是否"互相抵消" |

### 2.2 指标

- 主指标：各条件的 Acc(融合分) 及相对 C0 的 ΔAcc；**顺序敏感度 OS = Acc(C0) − mean Acc(C2)**，配对 95% CI。
- 分支分解（P1/P2 修复后才有意义）：Acc(仅语义分)、Acc(仅视觉分)。**内置 sanity check**：文本扰动只应改变语义分支——若 vis-only 精度在 C1/C2 下变了，代码有错。
- 得分层面：正确类的语义匹配分与 margin 在扰动前后的分布变化（为论文画图备料）。

### 2.3 实现切入点（基于仓库实读）

- **推荐做法：诊断专用脚本**。复制 `run.py` 的 `test()` 为 `diagnose()`：每个 episode 内，视觉前向做**一次**（`z_query/z_proto/q_aft_tm` 复用），文本侧对 6 个排列各算一次语义分——所有条件落在**同一批 episode** 上，天然配对、方差最小，且额外成本只有文本前向。排列的施加点：`models.py:91` 处 `self.entxt[i]['sub_act_en_li']` 的列表顺序（建议把排列作为 forward 的可选参数传入，而不是改 YAML 文件，便于同一 episode 内循环）。
- 帧扰动：在 `test()` 拿到 `x` 并 reshape 出 [n_way, sq, T, ...] 后，对 query 部分（`sq` 维的后 n_query 个）的 T 维做 `flip`/固定排列。**注意 O-2**：查询之间存在批内注意力，帧扰动必须对全部 5 个查询同步施加，结论解释时也要记得这层交互。
- **等变性单元测试（M1 就做，先于一切诊断结论）**：取一个 episode，比较「排列后的 3 段文本 → 编码特征」与「原顺序特征按同一排列重排」的逐元素差。若数值级一致 → O-1 成立，§3.2 的免费负样本可用；若不一致 → 撤回 O-1 表述，按实测行事。二十行代码的事，收益极大。

### 2.4 评测协议

- 开发期：600–2500 episode 定稿实验设计与代码；终表：10000 episode（与仓库默认口径一致，均值 ± 1.96·std/√n）。
- 复现性：沿用全局种子 916；诊断脚本内部涉及的随机排列单独设种子并写进日志；所有条件共用同一 episode 流。

### 2.5 结果解读的三个预注册分支（无论落在哪支都有产出）

1. **OS ≈ 0（不敏感）**：说明"三段子动作 + 阶段匹配"实际未利用顺序 → 3b 正则的动机极强，论文主叙事成为"声明 → 检验不通过 → 显式监督修复"；结合 O-1 可精确归因："架构等变 + 特征无阶段特异性"。
2. **OS 显著 > 0（敏感）**：首次实证了 TA++ 的顺序声明（本身即可写入论文），且由 O-1 可把敏感性**精确归因到式(16) 的阶段-窗口耦合**——比"模型懂顺序"泛泛之谈锐利得多；3b 转为增强角色，预期增益小。
3. 后续扩展到场景型数据集（Kinetics/HMDB）若不敏感而 SSv2 敏感：数据集级结论，正好呼应论文 Fig.9/文本深度的讨论。

## 三、阶段 2：顺序对比正则（3b，M5–M6）

### 3.1 损失设计

`L = L_CE + λ·L_order`，其中 L_CE 保持 run.py 现状（`CE(vis*sem*64)`）。L_order 两个候选，**先做 margin 版**（超参直观）：

- margin：对 episode 内每个类 c 及采样的非恒等排列 π，`max(0, γ − (s_c(正序) − s_c(π)))`，s 为该类文本与其对应查询的语义匹配分（式(16) 口径，即代码里的 cos_score 通路）。
- InfoNCE：正例=正序，负例=m 个采样排列（备选，二期再比）。

监控项：L_order 与 L_CE 的量级比、训练曲线是否互相压制。λ、γ 各扫一个小网格（具体取值首轮试跑后定，不预设）。

### 3.2 负样本工程（O-1 的免费午餐）

- 若等变性单元测试通过：**排列文本的特征 = 原特征按索引重排** → 训练中所有 5 个负排列的特征都可以从 `enh_embedding` 直接 index 得到，**零额外文本前向**，L_order 近乎零开销。这同时揭示：正则的梯度只能经由"阶段-窗口匹配"通路去塑造**特征的阶段特异性**——这正是我们想要的监督方向。
- 若测试不通过：退回真实文本前向，每 episode 每类采 1–2 个负排列控制开销（基线每 episode 已有 15 次文本前向，全排列会 ×6）。
- 硬负扩充（二期可选）：帧反转视频 vs 正序文本；跨类阶段错配。

### 3.3 训练与验收

- 以 B0 配置为底，只加 L_order；每组配置：训练 → 10000 episode 测试 → **重跑 §2 诊断**。
- 验收三件套：① Acc 相对 B0 的变化（±CI）；② OS 应上升（"模型变得会用顺序"的直接证据）；③ Fig.10 风格的分时刻精度曲线是否更尖锐（阶段区分更清晰）。
- 消融表模板：{B0, B0+L_order(λ₁), B0+L_order(λ₂), …} × {Acc, OS, 分支 Acc}。

## 四、实验管理规范（本轮顺带建立的流程习惯）

1. **一实验一目录**：仓库本身按时间戳建 checkpoint 目录并写 log.txt，沿用之；`config.yaml` 的 `message` 字段会写进日志——每次实验用它注明配置代号。
2. **配置快照**：每次运行把 config.yaml 复制进实验目录。
3. **版本管理**：fork 仓库；P1、P2 修复各自独立 commit（保证可回溯"修复前后"差异）；诊断脚本与正则在分支上开发。
4. **主结果台账**：一张 CSV：实验名 / commit 哈希 / 配置摘要 / Acc±CI / OS / 耗时 / 备注。所有进论文的数字必须能从台账回溯到 commit。
5. **GPU 习惯**：先小规模试跑再放全量；每类新实验首跑记录 `nvidia-smi` 显存峰值与墙钟。

## 六、风险清单与应对

- **复现落差 > 1 个百分点**：先查数据（划分、抽帧、帧数字段、采样协议），再查 CLIP 权重来源与 fp16 路径，最后才动超参。
- **P2 修复导致基线相对论文移动**：属预期；以 B0 为准，论文中如实说明修复及其影响。
- **等变性测试不通过**：撤回 O-1 相关表述与免费负样本方案，改真实前向，其余设计不变。
- **诊断显示完全不敏感且正则无增益**：叙事重心转为"诊断 + 归因"（结合 O-1 的架构分析仍是完整贡献），正则降为辅助尝试。
- **上游 Task-Adapter 仓库的数据说明与本仓库不一致**：以能复现到 63.6 附近的配置为准，并把差异记入台账。
